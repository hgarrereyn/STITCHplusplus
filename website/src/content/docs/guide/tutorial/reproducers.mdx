If an edit removes the bug, `stitch try` says so. Here the key is `a` instead of `tmp`:

<RunOutput name="try-bad" />

This short file is what you send to the library's maintainers. `stitch report <id>` (the crash id
you shrank) packages it for them: a `Dockerfile` that builds the library at the pinned commit (package versions as of when
the crash was found), the file, `run.sh`, and `ISSUE.md`, the text of a GitHub issue. Nobody needs
STITCH++ to run it:

```sh
stitch report <id>
cd .stitch/reports/<id> && ./run.sh     # Docker, or STITCH_RUNTIME=podman ./run.sh
```

## Is it fixed upstream?

When the project's source is a git repository (`stitch init --git URL --rev REV`), you can run a
crash against other versions:

```sh
stitch exec c1 --rev HEAD      # does the newest code still crash?
stitch bisect c1               # the commit that introduced the bug
stitch bisect c1 --fixed       # the commit that fixed it
```

## Coverage

<RunOutput name="cov" />

When the report has a "never called" list, those are library functions that no stub calls. Writing
stubs for them is the next step: add them, then `stitch build` and `stitch probe` again.
`html/index.html` shows each line and branch the campaign never reached.

## What you have done

- described an API with stubs, objects and fuzzed parameters
- used the probe report to find a stub that wasted runs, and fixed it with a data type
- asserted a property with a check
- grouped crashes, separated three bugs, and reduced one to a few lines of library code

The finished harness is in `examples/<language>-demo/harness/`. It has a few more stubs than this
tutorial, including `put_all`, which takes a list of pairs from a decoder. [Concepts](/guide/concepts/)
covers the ideas in more depth, and [Reference › Languages](/reference/languages/python/) has the full
API for each language.
