## Run a campaign

<RunOutput name="fuzz" />

The campaign runs in the background. `--jobs` sets the number of workers, and `--secs` stops it
after a while; without `--secs` it runs until `stitch stop`. Running `stitch fuzz` again resumes
from the programs it kept. `stitch status --wait` waits for the end.

## List the crashes

<RunOutput name="crashes" />

Crashes are grouped by their kind and the innermost frames in the library. The number after the
id (`x10`) is how many saved programs are in the group.

## Look at one

Take the group whose frames go through `dump`, or `items`, which `dump` calls. `minimize` removes
calls and shortens inputs while the program still crashes the same way. `exec --trace` runs it and prints every call:

<RunOutput name="trace-tmp" />

A key that starts with `tmp` goes into the store (through `load` or `put`), `remove` removes it,
and then `dump` fails. In the library, `remove` skips the order list for keys that start with
`tmp`, so `dump` looks up a key that is gone.

## Harness bug or library bug?

Decide this for every crash:

- **Harness bug**: the stubs used the API wrong, for example a double free or a missing
  precondition. Fix the stub, run `stitch build`, and check that `stitch exec` with the crash id
  no longer crashes.
- **Library bug**: every call was valid use of the API. Make a reproducer (next page).

Here every call is valid: putting, removing and dumping are always allowed, so this is a library
bug.

## The other groups

The other groups come from two more bugs. A value that starts with `#!` makes `load` crash; it
should reject the text instead:

<RunOutput name="trace-hash" />

A key that contains `=` does not survive `dump` and `load`: `load` splits the line at the first
`=`, so the key comes back different, or empty and rejected. `roundtrip` catches it:

<RunOutput name="trace-eq" />
