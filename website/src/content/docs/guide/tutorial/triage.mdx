## Run a campaign

```sh
stitch fuzz --jobs 2 --secs 60
stitch status
```

```
campaign 'main': running
  24s, 275k execs (11.4k/s), 64 edges, corpus 32, calls bailing 16% (programs with a bail 54%), 50 crash/timeout programs saved
```

The campaign runs in the background. `--jobs` sets the number of workers, and `--secs` stops it
after a while; without `--secs` it runs until `stitch stop`. Running `stitch fuzz` again resumes
from the programs it kept. `stitch status --wait` waits for the end.

## Look at one

```sh
stitch minimize c5
stitch exec c5 --trace
```

`minimize` removes calls and shortens inputs while the program still crashes the same way. `exec
--trace` runs it and prints every call:

```
[stitch] #0 load(text=Str[0,decoded]"")
[stitch]     -> ok produced o0.0
[stitch] #1 put(st=o0.0, key=Str[3]"tmp", value=Str[0]"")
[stitch]     -> ok
[stitch] #2 remove(st=o0.0, key=Str[3]"tmp")
[stitch]     -> ok
[stitch] #3 roundtrip(st=o0.0)

[stitch] EXCEPTION in roundtrip: KeyError: 'tmp'
    #0 0x0 in Store.items /opt/venv/lib/python3.12/site-packages/kvlib/__init__.py:26
    #1 0x0 in Store.dump /opt/venv/lib/python3.12/site-packages/kvlib/__init__.py:29
    #2 0x0 in roundtrip /project/.stitch/build/app/harness/stubs.py:40
```

Put `tmp`, remove it, then dump: `dump` fails. In the library, `remove` skips the order list for
keys that start with `tmp`, so `dump` looks up a key that is gone.

## Harness bug or library bug?

Decide this for every crash:

- **Harness bug**: the stubs used the API wrong, for example a double free or a missing
  precondition. Fix the stub, run `stitch build`, and check that `stitch exec c5` no longer
  crashes.
- **Library bug**: every call was valid use of the API. Make a reproducer (next page).

Here every call is valid: putting, removing and dumping are always allowed. `c5` is a library bug.

The other groups:

```
[stitch] #0 load(text=Str[5,decoded]"#!=#!")

[stitch] EXCEPTION in load: IndexError: list index out of range
```

`c1`: a value that starts with `#!` makes `load` index past the end of a list. `load` should reject
the text with a `ValueError`, not crash. `c2` is the same bug, reached through `roundtrip`.

```
[stitch] #1 put(st=o0.0, key=Str[2]"\xb7=", value=Str[0]"")
[stitch]     -> ok
[stitch] #2 roundtrip(st=o0.0)

[stitch] CHECK FAILED: dump/load roundtrip (node 2)
```

`c4`: a key that contains `=` comes back from `load` as a different key. `c3` is the same bug with
the key `=`: it comes back as an empty key, and `load` raises `ValueError` on the output of `dump`.

Five groups, three bugs. One bug can show up as several groups, so fix or explain one group before
judging the next.
